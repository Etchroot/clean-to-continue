# Clean to Continue 개발 요약 및 후기

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | Clean to Continue |
| 장르 | 제한형 3D 힐링 청소 게임 |
| 개발 목적 | OpenAI Game Builders Seoul 출품 및 Codex 기반 게임 제작 실험 |
| 개발 기간 | 2026년 8월 15일~23일, 달력 기준 9일(실제 경과 약 8일) |
| 엔진 | Unity 6.3 LTS, Universal Render Pipeline |
| 실행 환경 | 설치 없이 실행되는 Unity WebGL |
| AI 개발 도구 | Codex Desktop, Unity 공식 MCP Server |
| 플레이 시간 | 약 4~5분 |
| 주요 스테이지 | 마우스 → 키보드 → 헤드셋 |
| 최종 검증 | EditMode 26개, PlayMode 63개 자동 테스트 |

## 2. 프로젝트 목표

- 제작자가 C# 코드를 한 줄도 직접 입력하지 않고, 자연어 지시만으로 자신이 생각한 게임을 어디까지 구현할 수 있는지 확인한다.
- 짧은 개발 기간 안에 기획, 구현, 테스트와 Web 배포까지 하나의 완성된 흐름으로 연결한다.
- Codex를 단순 코드 작성 도구가 아니라 Unity Editor를 함께 다루는 개발 에이전트로 활용한다.
- 비전공자도 이후 구조를 이해하고 수정 방향을 제시할 수 있도록 개발 과정과 Human-in-the-loop 결정을 문서로 남긴다.

Codex 사용량은 정확한 API 계측값이 아닌 사용자 체감 추정치다. ChatGPT Plus 주간 사용 한도의 약 250%, 즉 약 2.5주 분량을 한 주 안팎의 집중 개발 기간에 사용한 수준으로 추정한다.

## 3. 게임 기획

### 핵심 콘셉트

오랜만에 게임을 하려고 책상 앞에 앉았지만 장비에 먼지가 쌓여 있다. 플레이어는 마우스, 키보드와 헤드셋을 차례로 청소한다. 장비 하나를 복원할 때마다 게임과 함께 성장했던 시절의 추억이 이미지와 한 줄 문장으로 되살아난다.

### 핵심 재미

- 먼지와 무광택 상태가 사라지는 즉각적인 시각 변화
- 에어건과 헝겊의 서로 다른 소리와 반응
- 장비를 돌려 남은 오염을 찾는 탐색
- 원형 복원도가 차오르고 완료 차임이 울리는 성취감
- 오락기 구경, 친구와의 게임, PC방의 환호로 이어지는 감정적 보상

### 플레이 규칙

- 좌클릭 드래그: 선택한 도구로 청소
- 우클릭 드래그: 장비 회전
- `Space`: 남은 오염 부분을 잠시 강조
- 에어건: 먼지 제거
- 헝겊: 표면 광택 복원
- 전체 복원도 90% 도달: 남은 오염을 자동 정리하고 스테이지 완료

### 씬 흐름

1. `01.MainMenu`: 인트로 영상, 시작·설정·크레딧
2. `02.Opening`: 검은 화면 위에 순차적으로 나타나는 독백
3. `03.Mouse`: 기본 조작을 배우는 첫 청소
4. `04.Keyboard`: 넓은 표면과 키 사이를 청소하는 두 번째 단계
5. `05.Headset`: 안쪽과 뒤쪽까지 돌려 보는 마지막 단계
6. `06.Ending`: 엔딩 이미지, 감사 문구와 처음으로 돌아가기

## 4. 개발 환경과 협업 방식

### Codex–Unity 연동

- Unity 공식 MCP Server의 Bridge와 Codex 클라이언트를 연결했다.
- Codex가 현재 열린 Scene, GameObject, Component와 Unity Console을 직접 확인했다.
- Codex가 Unity Editor용 C# 명령을 실행해 씬 생성·수정, 테스트 실행과 WebGL 빌드를 수행했다.
- MCP 연결이 도메인 리로드로 잠시 끊기면 파일 편집과 Editor 로그 확인을 사용하고, Bridge가 복구된 뒤 같은 작업을 이어갔다.

### 역할 분담

**사람이 담당한 일**

- 게임 소재, 제목, 플레이 흐름과 감정적 목표 결정
- 사용할 3D 모델·이미지·영상·음원 선택
- 책상, 벽과 장비의 크기·위치 조정
- Unity 및 Web 빌드 직접 플레이
- 청소 감각, UI, 오디오와 연출에 대한 수정 지시
- Codex가 제시한 설계와 최종 결과 승인

**Codex가 담당한 일**

- 기획을 구현 가능한 시스템과 작업 순서로 구체화
- C# 런타임 코드, ShaderLab 셰이더, Editor 빌더와 UI 구현
- Asset Store 프리팹의 메시·UV·재질·Collider 분석
- 자동 테스트 작성, 실패 재현, 디버깅과 회귀 검증
- Unity 씬 구성, WebGL 빌드와 배포용 ZIP 생성
- 비전공자 가이드, 개발 로그, Human-in-the-loop 및 제출 문서 작성

## 5. 개발 과정

### 1단계 — 아이디어와 범위 확정

- 청소 게임의 핵심을 ‘깨끗해지는 만족감’으로 정했다.
- 일반적인 소품 대신 게이머에게 친숙한 마우스·키보드·헤드셋을 선택했다.
- 자유 이동이나 복잡한 유체 물리는 제외하고 중앙 장비 하나에 집중하는 3D 구조로 범위를 제한했다.
- 제목을 `Clean to Continue`로 확정했다.

### 2단계 — 프로젝트와 개발 환경 구축

- Unity 6.3 LTS Universal 3D 프로젝트와 Web Build Support를 설치했다.
- Input System 호환 문제를 해결하고 Unity MCP Bridge 연결을 검증했다.
- `AGENTS.md`, 개발 로그, Human-in-the-loop와 제출 문서 구조를 먼저 만들었다.
- GitHub에는 자체 코드와 문서만 공개하고 Asset Store 원본은 제외하는 정책을 세웠다.

### 3단계 — 청소 시스템 세로 슬라이스

- 마우스 스테이지를 기준으로 도구 선택, 입력, 진행도, 청소 표현과 완료 흐름을 연결했다.
- 시각 표현은 512×512 GPU 마스크, 진행도는 64×64 CPU 격자로 분리했다.
- 같은 위치를 반복해서 닦아도 진행도가 중복 증가하지 않도록 했다.
- 먼지와 광택을 별도 레이어로 관리하고 90%에서 완료 이벤트가 한 번만 발생하도록 했다.

### 4단계 — 실제 프리팹 적용과 3개 스테이지 확장

- 사용자가 선택한 마우스, 키보드, 헤드셋 프리팹을 분석했다.
- 마우스와 키보드는 UV 기반 마스크를 사용했다.
- UV가 모두 한 점에 겹친 헤드셋은 클릭 주변 오버레이 삼각형을 제거하는 방식으로 전환했다.
- 공통 `StageRoot`와 입력·진행도·UI 코드를 세 장비가 공유하도록 구성했다.

### 5단계 — 연출과 전체 게임 흐름 완성

- 인트로 영상, 메인 메뉴, 설정, 크레딧, 오프닝과 엔딩을 연결했다.
- 장비 완료 시 AI 생성 추억 이미지, 회상 문구와 완료 차임을 표시했다.
- 따뜻한 책상 조명, 라운드 UI, 버튼 호버와 씬 전환 페이드를 적용했다.
- 배경음, 에어건·헝겊 소리와 모든 버튼의 클릭음을 연결했다.

### 6단계 — WebGL 검증과 반복 수정

- Unity WebGL 빌드를 itch.io에 업로드해 실제 브라우저에서 플레이했다.
- 한글 누락, 오디오 자동 재생, 씬 전환 후 무음, UI 잘림과 엔딩 버튼 문제를 업로드본에서 다시 확인했다.
- 사용자 플레이 피드백을 바탕으로 수정하고 같은 문제가 돌아오지 않도록 자동 테스트를 추가했다.
- 최종 업로드용 ZIP은 루트에 `index.html`, `Build`, `StreamingAssets`, `TemplateData`가 바로 위치하도록 만들었다.

## 6. 핵심 구현

### 하이브리드 청소 표현

- 유효한 UV가 있는 메시: RenderTexture 기반 실시간 마스크
- UV가 없는 메시: 클릭 주변의 오버레이 폴리곤 제거
- 에어건과 헝겊: 먼지·광택 레이어를 독립적으로 처리
- MaterialPropertyBlock: 원본 재질을 직접 손상하지 않고 런타임 속성 전달

### 진행도와 완료

- 실제 청소 가능 영역만 진행도 대상으로 등록
- 이미 청소한 영역은 중복 계산하지 않음
- 먼지와 광택 진행도를 같은 비중으로 합산
- 89.9%는 진행 중, 90% 도달 시 한 번만 완료
- 완료 후 입력과 중복 씬 이동 차단

### Web 친화적 구조

- Compute Shader 없이 더블 버퍼 RenderTexture 사용
- Input System 기반 마우스·키보드 입력
- 브라우저 사용자 입력에서 오디오 재활성화
- 한글 폰트를 프로젝트에 포함해 Web 환경의 시스템 폰트 차이 제거
- 사용하지 않는 Asset Store 데모와 빌드 캐시는 공개 저장소 및 Web 빌드에서 제외

## 7. 주요 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| 마우스 일부가 청소되지 않음 | 화면은 LOD0, Collider는 LOD3 사용 | 표시 메시와 청소 Collider를 LOD0로 통일 |
| 키보드가 87%에서 멈춤 | UV 사각형의 빈 공간까지 진행도에 포함 | 실제 UV 삼각형과 겹치는 격자만 계산 |
| 헤드셋 파츠 전체가 한 번에 변함 | 모든 UV가 `(0,0)`에 겹침 | 클릭 주변 오버레이 삼각형 제거 방식 추가 |
| 헤드셋 `Muffs`가 청소되지 않음 | 부모 파츠가 자식 클릭을 먼저 소비 | 실제 클릭된 Collider의 레이어를 우선 선택 |
| Web에서 한글 UI가 사라짐 | 기본 폰트와 짧은 Text 영역 | Noto Sans CJK KR 포함 및 영역 확대 |
| Opening부터 BGM이 들리지 않음 | 씬의 AudioListener 누락과 Web 자동 재생 제한 | 씬별 리스너 보장 및 버튼 입력에서 재생 재시도 |
| Ending 버튼이 반응하지 않음 | UI 입력 모듈 누락 | EventSystem과 Input System UI Module 보장 |
| 도구 이미지가 가로로 늘어남 | 정사각형 이미지가 Sliced로 설정됨 | Simple과 Preserve Aspect 적용 |
| 자동 씬 생성이 사용자 배치를 덮을 위험 | 생성 영역과 사용자 영역 미분리 | 프로젝트 소유 루트만 재생성하고 사용자 Transform 보존 |

## 8. 테스트와 결과

- 규칙과 데이터 계산은 EditMode 테스트로 검증했다.
- 실제 Camera, Collider, Input System, UI와 AudioSource 흐름은 PlayMode 테스트로 검증했다.
- 새 기능이나 버그 수정은 가능한 경우 실패 테스트를 먼저 만든 뒤 최소 수정으로 통과시켰다.
- 최종 자동 검증은 EditMode 26개, PlayMode 63개가 통과했다.
- 최종 WebGL 압축 파일은 18개 항목과 루트 `index.html`을 포함한다.
- 전체 게임은 별도 설치 없이 브라우저에서 실행되며 마우스·키보드·헤드셋과 엔딩까지 하나의 흐름으로 연결된다.

## 9. 프로젝트 결과와 한계

### 결과

- 자연어 지시와 Unity Editor 조작만으로 플레이 가능한 3D Web 게임을 완성했다.
- 서로 구조가 다른 세 외부 프리팹에 하나의 공통 청소 경험을 적용했다.
- 사용자 피드백, Codex 구현과 자동 테스트가 반복되는 Human-in-the-loop 개발 흐름을 실제로 운영했다.
- 코드, 문서, 테스트와 Git 이력을 통해 Codex가 수행한 작업과 사람이 결정한 내용을 구분했다.

### 한계와 후속 과제

- Asset Store 원본은 라이선스 때문에 GitHub에 포함하지 않으므로 저장소만 내려받아서는 최종 화면이 완전히 복원되지 않는다.
- 3D 모델의 수동 배치와 미세한 연출 판단은 사람이 직접 처리하는 편이 더 빠른 경우가 있었다.
- 공개 플레이 URL, 썸네일과 데모 영상은 해커톤 제출 폼에 별도로 입력해야 한다.
- 향후에는 더 복잡한 게임 상태, 저장 시스템과 장기 플레이 구조에서도 같은 개발 방식이 유효한지 확인할 필요가 있다.

## 10. 개발 후기

이번 프로젝트의 주요 관점은 코드를 한 줄도 직접 작성하지 않고, 내가 생각한 것을 게임으로 얼마나 구현할 수 있는지 확인하는 것이었다.

Codex의 속도와 결과물의 품질도 상당했지만, 특히 놀라웠던 점은 작업 수행 능력이었다. Unity MCP를 이용해 개발했는데, 대부분의 기능을 생각한 방향대로 구현했을 뿐 아니라 자동 테스트와 빌드까지 직접 실행하고 결과를 검증했다.

프리팹의 메시와 폴리곤 구조를 분석해 새로운 오염 오버레이를 만들고, 게임의 분위기와 플레이 방식에 맞춰 조명과 카메라를 배치하는 모습을 보면서 “이런 것도 할 수 있다고?”라는 생각이 계속 들었다. 자동 테스트로 오류를 선제적으로 발견하고 같은 버그가 반복되지 않게 한 점도 인상 깊었다.

아직 메커니즘이 복잡한 게임을 만들어 보지는 않아 모든 장르에 대해 단정할 수는 없지만, 비교적 단순한 게임에서는 제작 시간을 크게 줄여 줄 수 있을 것 같다. 오브젝트의 위치와 크기를 조정하는 것처럼 단순하고 시각적인 작업은 아직 사람이 직접 하는 편이 더 빠르고 정확한 경우가 있었다. 그럼에도 초보 개발자나 1인 개발자의 입장에서는 획기적인 효율을 보여 주는 도구임이 틀림없다.

AI 에이전트가 발전하면서 인간 개발자에게 필요한 역량의 중심도 코딩 자체에서 연출과 게임에 어울리는 재료를 찾는 안목으로 넓어지고 있는 듯하다. 모델링, 이미지와 사운드 등 여러 생성형 AI를 활용하고 그 결과물을 자연스럽게 연결하는 능력을 기른다면, 앞으로는 AI를 적극적으로 활용해 A급 품질의 게임을 만드는 1인 개발자도 등장할 수 있지 않을까 생각한다.
